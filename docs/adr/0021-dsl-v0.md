# ADR-0021：DSL v0 —— 声明式图 API 与执行语义

- **状态**：已接受（v0.5 增补见文末：join 原语，多消费者约束解除）
- **日期**：2026-08-27
- **决策者**：Pride Leong
- **关联**：[adr/0001](./0001-dsl-form.md) · [adr/0019](./0019-coroutine-strategy.md) · [adr/0022](./0022-lineage.md)

---

## 背景

ADR-0001 定了 DSL 的**形式**（fluent builder、C++ 内嵌、flow 函数即程序），但没定两件落地必须回答的事：

1. **声明与执行的关系**——builder 记录的图怎么变成运行的东西？
2. **与 L4 运行时（Component/Dispatcher）的关系**——DSL 是翻译成 L4 算子，还是自成执行路径？

此前一版 flow.h 草稿（闭包塞进声明结构体、"executed once"占位语义）被撤回，根因就是没先回答这两个问题。

## 候选方案

### 方案 1：DSL → 代码生成 → Component（编译期路线）

DSL 声明经 L1 编译器生成 Component C++ 代码再编译运行。

**否决（现阶段）**：L1 编译器是 Phase 2 目标；Phase 1 需要 DSL 立即可跑用于验证 H1 链路。且 codegen 形态本身有待定 ADR（见队列）。

### 方案 2：DSL → 即时解释执行（interpretation）

builder 记录图；`run()` 时解释器直接在 L4 运行时上拼装：map 级联翻译成 Component + DataVisitor 链，source 翻译成 TimerSourceComponent。

**选定理由**：
- 声明即执行，零生成步骤——Phase 1 的 demo 需求精确匹配
- **图记录格式与解释器解耦**：v0 的 FlowDecl 结构体就是将来 L1 编译器的 IR 输入雏形，解释器只是 IR 的第一个消费者
- 与 ADR-0019 一致：回调语义，无协程

### 方案 3：DSL → 惰性图 + 拉取执行（pull-based）

声明构建依赖图，sink 消费时反向拉取求值（Reactive/Flink 风格）。

**否决（现阶段）**：与 L4 推送式运行时（Dispatcher 派发）语义相反；流式传感器场景推送是正解。留给 Phase 3 的批处理/回放场景评估。

## 决策

**方案 2**。API 与执行语义如下锁定：

### API 形态（v0）

```cpp
auto flow = tianshu::dsl::Flow("demo")
    .source<SensorMsg>("imu", 10ms, [](uint64_t tick) { return make_imu(tick); })
    .map<SensorMsg, FusedMsg>([](const SensorMsg& in) { return fuse(in); })
    .map<FusedMsg, OutMsg>([](const OutMsg&...) ...)
    .sink<OutMsg>([&](const OutMsg& out) { results.push_back(out); })
    .build();

flow.run_for(1s);   // 解释执行
```

- `source<T>(name, interval, fn)`：定时源（传感器替身），通道名 `flow/<name>`
- `map<TIn, TOut>(fn)`：纯函数级联，自动接线匿名通道 `flow/~N`（类型即约束——Stream\<T\> 句柄只能接 T 匹配的下一跳）
- `sink<T>(fn)`：终端回调（观察/记录/断言）
- **map 隐式携带血缘**：输出 Message 的 lineage 记录 `(输入通道, 输入 seq)` 级联链（细节归 ADR-0022）

### 执行语义（v0 解释器）

1. `build()` 产出**不可变** `Flow`（声明图：源/映射/汇的强类型节点表）
2. `run_for()`：解释器把声明图装配到 L4 运行时——每个 source 一个定时线程，经 `FlowRuntime::publish_bytes` **直连 DataDispatcher**（同步级联：一次 publish 在同一调用栈内贯通全链）；每个 map 一个 DataVisitor + 回调执行 fn 再 publish；每个 sink 一个 DataVisitor 消费。v0 不经过 transport Writer/Reader——INTRA 通路留给 L1 编译器输出，解释器保持确定性的单线程级联语义
3. **v0 单消费者约束**：每个通道至多一个下游（链式 DSL 天然满足；对中途分叉 sink 的显式约束）。原因见 ADR-0022 血缘旁路模型
4. 类型擦除点只有一个：map 内部以 `MessageTraits<T>::serialize/deserialize` 过缓冲（POD 即 memcpy），与 L4 typed 通路一致
5. v0 单线程级联语义（每条链在其 source 线程内同步贯通），不承诺并行度——那是 L1 编译器 + SLA 规划（L3）的事

### 与 L1 编译器的关系（前瞻约束）

- FlowDecl 的字段就是 IR 字段的 v0 子集：节点类型、通道、类型名、连接
- 解释器实现放在 `tianshu::dsl::runtime` 命名空间，编译器未来替换它时**Flow API 与声明格式零变化**
- SLA 标注（周期/deadline）在 API 上预留 `.with_sla()` 位（v0 接受但忽略），编译器消费

## 影响范围

- 新增 `tianshu/include/tianshu/dsl/flow.h`（声明层）+ `dsl_runtime.h`（解释器）
- demo：`examples/dsl_demo.cc`——source→map→map→sink 三跳级联 + 血缘打印（与 ADR-0022 demo 合一）
- 功能点：L1-DSL-1..3 的 v0 子集进开发计划

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 解释器性能不代表编译器性能 | v0 只验证语义与 H1 链路；benchmark 结论不外推 |
| API 过早冻结 | `with_sla` 预留但不实现；有损变更走 0.x 语义版本 |
| 与 Component 路线重复 | 解释器**复用** Dispatcher/Visitor，不另起炉灶；transport 通路由 L1 编译器接入 |

## v0.5 增补（2026-08-28）：join 原语

> v0.6 起增加 box 原语（带端口与生命周期的读写一体节点，驱动/底盘复用的基础）——见 [adr/0024](./0024-dsl-box-primitive.md)。

- `FlowBuilder::join<A, B, C>(chainA, chainB, fn)`：两流 AllLatest 融合（`DataVisitor<A, B>`，两输入皆非空才触发，各消费一条——与 L4-COMP-6 同语义）
- 链式 API 不再是唯一形态：`source` 返回的 `FlowChain` 可先持有，再交给 `join` 组合（扇出 DAG 声明）
- **解除单消费者约束**：血缘改为每消费者邮箱（ADR-0022 v0.5 增补），同一通道可挂多个 sink/join
- 输出血缘合并两父分支集，join hop 追加到每条分支
- 约束保持：join 的输出通道仍为匿名中间通道；`with_sla` 仍为注解槽
